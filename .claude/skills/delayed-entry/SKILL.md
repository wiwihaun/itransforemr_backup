# 延遲進場（entry_at）：語意、實作與已知陷阱

## 這個機制是為了解決什麼問題（不是「濾雜訊」）

延遲進場常被直覺理解成「等訊號持續出現、過濾掉單根雜訊」，但這不是它在這個專案裡的起源。真正的起源是 Round 2 發現的一個更具體的問題：**停損出場後隔 4 小時就能立刻再進場，導致反覆撞同一個市場狀態**——17 次立即再進場裡有 9 次是停損接停損，最長 8 連損吃掉 16 個百分點。改成「叢集優先」（同一叢集只進場一次）之後，主要操作點報酬從 +23.86% 提升到 +51.84%，最大回撤從 −21.57% 收斂到 −11.50%，交易數從 49 降到 33。

`entry_at`（等到叢集第 N 根才進場，而不是第一根）是後來 Round 5 才加的，而且**是使用者明確指定的需求，不是資料驅動發現出來的技巧**——使用者原文是「叢集發生第 6 根開始進場」。這個區分值得記住：不要把 `entry_at` 的存在本身當成「這樣做能提高勝率」的證據，它解決的是另一個問題（避免同叢集重複進場），至於延遲到第幾根對報酬有沒有幫助，是需要另外驗證的、獨立的問題（見下面第 4 節，答案並不樂觀）。

---

## 兩套實作，邏輯必須一致，型別故意不同

| | backtest | 實盤 |
|---|---|---|
| 檔案 | `toolbywi/r2_experiments.py` 的 `stream_entry()`；`toolbywi/ablation.py` 有獨立一份同邏輯拷貝 | `live_trading/strategy.py` 的 `update_cluster_state()` |
| 狀態的「時間」單位 | 陣列 index（`k = orig_rows[j]`） | 真實時間戳（`pd.Timestamp`） |
| 狀態存在哪 | Python 迴圈區域變數 | Firestore（每個 tick 是獨立的 Cloud Run Job 執行，狀態不能留在記憶體） |
| 因果性自我測試 | `stream_entry(entry_at=0)` 必須逐筆等於向量版 `single_pos()` | `update_cluster_state()` 必須逐筆等於逐字照搬的 `_reference_cluster_logic()`（合成機率序列、500 根、entry_at∈{1,3}） |

改 `GAP`、`entry_at` 判斷邏輯、或 cluster 邊界規則時，**兩邊都要改，而且兩邊的自我測試都要重跑**。這不是「順便check一下」的建議，是因為兩份實作是刻意分開維護的（型別不同、無法直接共用程式碼），沒有測試會不知道兩邊什麼時候悄悄分歧。

交接處有個容易漏掉的細節：`update_cluster_state()` 只回傳 `should_attempt`（這根K棒滿足進場條件），**不代表已經進場**。呼叫端（`main.py`）要自己確認目前沒有部位、沒有掛單（對應 backtest 裡的 `busy` 檢查）才能真的下單；如果當下 busy，不能呼叫 `mark_entered()`——要讓同一個 cluster 之後的根還有機會再嘗試進場。這跟 `stream_entry()` 遇到 `k <= busy` 時只 `continue`、不設 `entered=True` 的行為是對齊的：

```python
# live_trading/strategy.py
should_attempt = (not entered) and (cluster_count >= entry_at)
return new_state, should_attempt
# 呼叫端只有在真的下單成功後才呼叫：
# state['cluster'] = strategy.mark_entered(state['cluster'])
```

## `entry_at=1` 是什麼意思（這個名字最容易被誤解的地方）

**`entry_at=1` = 叢集的第一根就進場，等於沒有延遲**，不是「延遲一根才進場」。`gap`（目前 =6）定義叢集邊界：前 `gap` 根內沒有訊號，下一個訊號才算新叢集的開始。

更重要的陷阱：`entry_at` 的語意是**「持續開放的進場窗口」**，不是「單次嘗試」——從第 N 根訊號開始，只要還沒進場，之後每一根滿足條件的訊號都會繼續嘗試，直到成功或叢集結束。這跟更早的 `cluster_first`（只在叢集第一根試一次，如果那根被既有部位擋住，整個叢集直接作廢，之後不再試）**不是同一件事**，即使在 `entry_at=1` 的設定下也一樣：

> 實測同一個門檻下，舊版 `cluster_first` 59 筆、新版 `entry_at` 67 筆，差距全部來自「第一根被部位擋住」的情況——舊版放棄整群，新版接著試下一根。

不要假設 `entry_at=1` 可以無痛相容舊版 `cluster_first` 的回測結果；兩者逐筆比對不會相同。

---

## `entry_at` 怎麼選：方法論正確，但可靠度有實測數據，不樂觀

選擇規則（避免測試集決策洩漏，見 [[no-lookahead-bias]]）：只在**驗證集**上選——top-20% 門檻下，候選（交易數 ≥ `min_trades`）中總報酬最高者；沒有候選滿足門檻就退回 `entry_at=1`。測試集的完整 `entry_at` 掃描只做事後描述，明確不用來重新選擇。驗證集本身還被早停、校準器擬合用過，不是完全乾淨的樣本。

這套規則本身沒有洩漏問題，但**可靠度是實測出來的，數字不好看**：R2 跟 R6 用完全相同的規則，R2 選中的 `entry_at=3` 在測試集上排名倒數（9 個候選裡第 6 名），R6 選中的 `entry_at=1` 剛好是測試集第一名。

> 只有 1,404 根 K 棒的驗證集，樣本量不足以穩定地把「驗證集上最好」對應到「測試集上最好」——尤其驗證集在 top-20% 門檻下，entry_at=3 只有 15 筆交易，這種規模的差異很容易被單筆交易的偶然結果主導……誠實的結論是「這個樣本量下，驗證集選擇的可靠度大概是丟硬幣等級」。

而且延遲進場的邊界選擇不是免費的午餐：兩個新配置（R2 的 entry_at=3、R6 的 entry_at=1）的門檻穩健性都從「通過」變成「不通過」。引用某一輪選出來的 `entry_at` 時，不要暗示這個值是「驗證過的最優解」——它只是「這套方法這次剛好/剛好沒選對」的其中一次結果。

## 市價 vs 限價，跟 `entry_at` 大小是耦合的，不能跨輪硬套結論

Round 6（R2 用 `entry_at=3`、R6 用 `entry_at=1`，訊號相對少）：限價單總報酬贏市價。Round 7（固定 `entry_at=1`，訊號較多）：**結果反過來**，市價贏限價——逐筆配對比較仍是限價平均較優（每筆便宜一點），但市價抓到的交易數量帶來的複利效果蓋過了單筆價差的改善。

> Round 6 報告呈現的兩個案例都是限價贏，容易讓人誤以為「限價單無條件比市價好」……市價 vs 限價哪個總報酬較高，取決於訊號數量、成交率、以及錯過訊號的機會成本三者的相對大小，沒有一個方向是穩贏的。

引用「限價比較好」或「市價比較好」的結論之前，先確認那一輪用的 `entry_at` 是多少，訊號數量級是否跟你現在的情境相近。

## 檢查清單

- [ ] 改了 `GAP` / `entry_at` / cluster 判斷邏輯 → `stream_entry()`（backtest）跟 `update_cluster_state()`（實盤）兩邊都要改
- [ ] 改完之後，兩邊的因果性自我測試都要重跑（backtest 版對比向量版 `single_pos()`；實盤版對比 `_reference_cluster_logic()`）
- [ ] 不要把 `entry_at` 跟其他策略參數（TP/SL、門檻、架構超參數）放進同一個測試集掃描裡選——`hparam_search.py` 特意把策略參數整組排除在架構搜尋外，就是為了不讓比較組數指數膨脹、踩到多重比較污染（見 [[no-lookahead-bias]]）
- [ ] 提到「entry_at=1」時講清楚是「叢集第一根、無延遲」，不要讓人誤解成「延遲一根」
- [ ] 新增/修改 `update_cluster_state()` 呼叫端邏輯時，記得 `should_attempt=True` 不等於「已進場」——只有真的下單成功才呼叫 `mark_entered()`
- [ ] 引用某一輪市價 vs 限價、或某個 `entry_at` 選擇結果時，先確認那一輪的設定（`entry_at` 值、訊號數量級），不要跨輪直接套用結論
